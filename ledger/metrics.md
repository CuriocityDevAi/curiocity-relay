# 방법론 효과 측정 — 3지표 (Kyu 11-10 15:01 승인 "숫자 3개를 relay에 기록하자")

목적: "이 방식이 효과적이다"를 느낌이 아니라 숫자로. 주 단위로 추세를 보고, 나빠지는 지표가 있으면 그쪽 프로세스/장치를 고친다.
기록자 = **오케** · 하루 마감(handoff 작성) 때 그날 줄 추가 · 원천 = 상태판 DB(`prompts/<ID>` 의 issued_at · landed_at · merged_at · tested_at · state) + relay 리포트(판정) + 오케 채팅 기록(Kyu 손작업) + `device-incidents.md`.

## 정의

**① 리드타임 (발부 → 머지)** — 제품 PR(앱·서버) 카드의 `merged_at − issued_at` 중앙값. 리뷰·도구·진단 카드 제외. 참고로 착지까지(`landed_at − issued_at`)도 같이.
**② 재작업률** — 그날 발부한 프롬프트 중 다시 손봐야 했던 비율. 셈: 폐기 후 재발부 · R0 CHANGES(코드) · 진단 오류 재진단 · 가짜 완료. 원인을 3갈래로 나눠 적음 — **코드**(허브 결과물 문제) / **진단**(분석 틀림) / **장치**(러너·오케·환경 탓으로 일이 안 돈 것).
**③ Kyu 손작업** — Kyu 가 해야 했던 일의 횟수. 2갈래: **장치 손작업**(/exit · 터미널 명령 · 수동 붙여넣기 · 회수 · 설치) = 줄여야 할 것 / **실기·판정**(아이패드 테스트 · 결정 답변) = 사람 몫이라 유지. 오케가 채팅에서 Kyu 에게 요청한 건수로 셈(분 단위 시간은 Kyu 가 원하면 추가).

목표 방향: ① 줄이기 · ② 장치 원인 0 에 가깝게 · ③ 장치 손작업 0 에 가깝게(실기·판정은 그대로).
