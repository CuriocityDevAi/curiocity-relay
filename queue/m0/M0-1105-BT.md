## [REQ] (계획서 §5-2 · §5-3 그대로)
1. `/refund-retry` body 에 `mode: "retry" | "cash_fallback"`(기본 retry · 후방 호환).
2. **mode=retry · QRIS 포션**: 실패 QRIS tender 를 `tryXenditRefund` 로 재호출 · 새 reference_id(이전 것 재사용 금지 · `retry:N`) · SUCCEEDED/PENDING → tender_results succeeded · 즉시 FAILED → failed 유지. 직전 refund 가 아직 PENDING 이면 409 `xendit_refund_still_pending`. CASH/CARD 포션은 기존 동작.
3. **mode=cash_fallback**: manager_pin 필수(400 `cash_fallback_requires_pin`) · 대상 없음 400 `cash_fallback_no_failed_qris` · Cash Movement `{type:"adjustment", signed_delta:-금액, reason:"return:<order>:<ret>:cash-fallback-qris"}` · tender_results[i].status=`succeeded_via_cash`(method 유지) · 영수증 kind = 기존 `resolveRefundReceiptKind`(Q4) · 응답에 `cash_movement_id` · `open_drawer:true`.
4. **이중 환불 가드**: (가드1) cash_fallback 진입 시 order.metadata 신선 재로드 → 그 return 의 xendit.status 가 SUCCEEDED 면 409 `cash_fallback_blocked_by_succeeded_xendit` · cash_fallback 과 웹훅 refund 핸들러를 `withOrderLock(order_id)` 로 직렬화(웹훅 refund 블록에 감쌈 추가). (가드2) 웹훅 SUCCEEDED 가 이미 `succeeded_via_cash` 인 entry 에 오면 x.status 만 기록 · r.status 불변 · `order.metadata.dup_refund_alerts[]` 경보 로그 · **자동 교정(돈 더 돌려주기/회수) 금지**(Q3).
5. 단일 QRIS 주문(`qris_refund_failed`)에도 같은 두 모드 동작.
6. 통합 테스트(신규 spec): (a) QRIS refund FAILED → retry → SUCCEEDED (b) FAILED → cash_fallback(PIN) → Cash Movement −금액 · succeeded_via_cash (c) cash_fallback 뒤 늦은 SUCCEEDED 웹훅 → 상태 불변 + dup_refund_alerts 1건 (d) xendit PENDING 중 retry → 409 (e) PIN 없음 400 · 대상 없음 400 (f) split(CASH+QRIS) 주문의 QRIS 몫 실패 → retry 동작 · CASH 몫 영향 없음 (g) 기존 refund-retry(A안 · CARD 승인번호) 회귀.
