## 의심 지점 (전부 확인 · 표)
1. 앱이 보내는 `payment_request_id` 가 **비어 있거나 다른 값**인지: QR 첫 발행 직후 currentPaymentRequestId 초기값이 어디서 오는지(tenders QRIS 응답 필드명 · qris-status 응답에서만 채우는 구조면 첫 폴링은 빈 값 → 400 → 영원히 못 채움 = 닭과 달걀). `undefined` 문자열 전송 여부.
2. 서버 `qris-status/route.ts` 가 `payment_request_id` 로 세션을 찾는 방식: `filters: { id: payment_request_id }` 가 **payment_session.id(= `payses_…`)** 를 기대하는데 앱은 Xendit **`pr-…`** 를 보내는지(또는 반대) — R0-DR 은 "payment_session.id = initiatePayment.id = pr-…" 라고 했지만 Medusa v2 에서 payment_session.id 는 자체 ULID 라 다를 가능성이 큼. 실제 값 대조.
3. 404 경로(주문 id 가 draft id `order_…` vs 완료 후 order id) · 403/401(관리자 토큰).
4. Simulate 라우트(#236)가 같은 주문에서 성공하는지 · 성공 후 웹훅(payment.capture)으로 captured 되면 qris-status 가 `captured` 를 주는지 — #BR-a 와 같은 통합 테스트에 **"tenders QRIS 응답 → 앱이 쓰는 그 필드로 qris-status 조회 → 200"** 을 추가해 실제 왕복을 재현.
